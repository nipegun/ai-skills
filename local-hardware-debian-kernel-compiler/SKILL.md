# Local hardware Debian kernel compiler

Produce a `linux-image-…deb` and matching headers for the **newest stable Linux release compatible with all required stable modules**, with the smallest defensible configuration for the target machine. Module compatibility takes priority over the kernel version number. Optimize the enabled feature set and installed kernel/modules size; do not equate fewer modules with a smaller kernel. Explain retained dependencies and uncertainty instead of promising a mathematically minimal configuration or guaranteed operation before booting it.

## Scope and invariants

- **Mandatory compatibility policy:** start with the newest final stable kernel and stable/production releases of every required external module, including a newer official stable driver when the installed release is obsolete. Verify the vendor's release classification. Never substitute a beta, RC, development snapshot or ad hoc module patch to force compatibility. If a required stable module cannot compile against that kernel, record the evidence and select the next lower supported stable candidate, including LTS branches, through `fetch_source.py --compatibility-report`. Reconfigure and rebuild for each candidate and repeat until every required module compiles. Never remove a required device to make a candidate pass. Exclude prerelease and EOL kernels. Missing tools, invalid configuration, OOM, download/signature errors or insufficient privileges require fixing the environment, not descending kernel versions. If no supported stable candidate works, report the unresolved modules rather than claiming a compatible result.
- Discover **the target computer**, not a build container's visible host kernel or a remote machine. A VM inventory targets that VM's virtual devices. Containers/chroots require an inventory and baseline from the actual target; do not infer the host from them.
- Hardware-only is insufficient for a usable Debian boot: retain the root-storage chain, filesystems, initramfs, firmware, user-space ABI, networking in use, security policy, power management and their dependencies. Remove unrelated drivers and optional software facilities only after establishing they are unnecessary.
- Treat missing information as unknown, never as absence. An unbound device, an unreadable report, or an unresolved alias must have a documented resolution before claiming full coverage. Disconnected peripherals need previous inventories or user-supplied requirements.
- Use read-only discovery; do not load/unload drivers, unbind devices, suspend the host, rewrite firmware, change boot settings, or install the result as part of package generation. Install/reboot only if separately requested. Do not add repeated approval steps for work already authorized.
- Build as an ordinary user in an isolated workspace. Root is only needed for dependency installation or otherwise unreadable inventory when authorized; do not assume `sudo` exists. Keep the running kernel and a bootable fallback.

## Workflow

1. **Check prerequisites and show the initial dependency notice.** Before running the inventory helper, downloading kernel sources or compiling, follow [the mandatory dependency notice procedure](references/build-and-delivery.md#initial-dependency-notice). Use basic read-only queries to identify the Debian release, architecture, execution environment, installed tools and versions. Tell the user which required packages are missing or outdated, why they are needed, and provide a copyable `apt install` command containing only the packages that need action, to run as root without `sudo`. Check that the configured repositories can supply suitable versions, including Python 3.13+. If nothing is missing, say so and continue without an empty installation command. Keep conditional requirements separate and update the notice when the source/configuration establishes them. Then read [references/discovery.md](references/discovery.md) and establish the target and workspace. Put all build files, downloads, temporary files and logs under the chosen workspace, normally `_/temp/kernel-build/` within the user's project. Use fresh directories for each run; do not modify `/usr/src/linux` or the installed module tree.
2. **Inventory and coverage.** Run `scripts/inventory.py --output-dir <new-directory>` on the target with Python 3.13+. Read its JSON and command reports; missing tools/errors are recorded. Supplement the automated snapshot as described in the reference. Build `coverage.tsv` mapping each device, boot requirement and active software feature to drivers, firmware and Kconfig symbols in the **new** source. Review candidate modules rather than blindly retaining every loaded module.
3. **Select stable modules and fetch a kernel candidate.** Read [the compatibility loop and report format](references/compatibility.md), then [source acquisition](references/build-and-delivery.md#source). Record required module families, their stable versions and official stability evidence before compiling. Use `scripts/fetch_source.py --work-dir <new-directory> --keyring <verified-release-keyring>`, adding `--compatibility-report <report-json>` after any incompatibility. The helper sorts supported final stable/LTS candidates in descending version order and skips only kernels with recorded stable-module incompatibilities. It verifies the uncompressed source signature before extraction. `--resolve-only` records selection without downloading sources. Selection alone does not prove compatibility.
4. **Reduce configuration.** Read [references/configuration.md](references/configuration.md). Start from the working target config, migrate it, and use a reviewed union of module evidence for `localmodconfig`. Then audit and prune built-in drivers, unnecessary subsystems and debug features explicitly. `localmodconfig` alone does not meet this skill's objective. Reconcile every required option against the new Kconfig dependency graph and run `olddefconfig` after each coherent change.
5. **Check the effective config.** Create an evidence-bearing `requirements.json` using [references/configuration.md](references/configuration.md#requirements-file). Run `scripts/audit_config.py --config <effective-config> --baseline <migrated-baseline> --requirements <requirements-json> --output <new-report-json>`. Resolve every failure and review the full diff, including newly enabled options. This helper checks declared requirements, not whether the declarations cover all hardware.
6. **Build all required modules and inspect packages.** Follow [references/build-and-delivery.md](references/build-and-delivery.md#build). Use upstream `make bindeb-pkg` with a unique local release suffix and bounded parallelism. Compile every required external module at its selected stable version against the actual generated headers. If any has a genuine kernel incompatibility, record it in the compatibility report and return to step 3 with a fresh candidate directory; repeat steps 4–6. A candidate passes only when all required modules and the kernel build successfully. Extract packages into staging and verify architecture, boot image, config, headers, module dependencies and modalias coverage. Account for firmware, initramfs and Secure Boot; report required driver/user-space updates separately from compilation success.
7. **Deliver.** Provide absolute paths, versions, hashes and sizes of the image/headers packages, `.config`, source/signature records, inventory, coverage map, requirements, config diff, build log and compatibility report. Distinguish successful packaging, offline checks and actual boot verification. Report a hardware/boot incompatibility as blocked compatibility, not as a working result. Give exact installation and rollback instructions without executing them unless requested.

## Boundaries that affect the result

- Preserve CPU mitigations, required LSMs, module signatures and boot trust requirements; these are not removable extras just because `lsmod` cannot see them.
- Firmware and microcode are separate from kernel source. Identify their Debian packages and required files; do not claim that a kernel image bundles them automatically.
- Required proprietary/out-of-tree modules must use verified stable releases. Exhaust newer eligible stable driver releases before rejecting the newest kernel; if stable modules still cannot compile, descend kernel candidates automatically with the recorded reason. Keep the module-version catalog consistent across attempts and re-evaluate stale failures when module versions change. Do not install driver updates as part of source/package preparation unless installation was requested.
- Do not retain entire unrelated driver families as a permanent shortcut. If a family must remain while evidence is incomplete, name it and mark minimization incomplete. Never disable an unresolved required function merely to reduce size.
- Modules share code and aliases, and devices can need several cooperating drivers. Kconfig dependencies, selected helpers and architecture infrastructure are legitimate retained code. Preserve hotplug support for the required device classes and all functions of composite devices.

## Helper interface

All three helpers use Python 3.13+ and the standard library. They refuse to replace their primary output. Read their source when adapting a workflow; they are supporting tools, not a one-command proof that a kernel will boot.

| Helper | Input | Output / side effects |
| --- | --- | --- |
| `inventory.py` | New output directory; optional repeated `--extra-module NAME` | Local JSON, baseline config, read-only reports and `candidate-modules.lsmod`; no driver loads |
| `fetch_source.py` | New work directory; authenticated keyring or `--resolve-only`; optional `--compatibility-report` | Descending stable/LTS selection, documented exclusions, verified archives/source; network access |
| `audit_config.py` | Effective config, baseline and requirements JSON | Config differences and requirement failures; exit 2 on unmet requirements |

Consult the official links in the references and the downloaded release's own Kconfig/build scripts when behavior differs between kernel versions. Never freeze a kernel version in this skill.
